# Requirements Document

## Introduction

Phase 4 extends the existing LinkedIn AI Content Generator (Phases 1–3) with an infographic generation pipeline. For each LinkedIn post (`PostModel`), the system produces a professional educational infographic PNG through a multi-stage pipeline: an LLM generates a structured `VisualSpec` JSON, an `ImageProvider` produces a background image, an HTML/CSS template composites the layout, and Playwright renders the final PNG. The result is persisted in a new `images` database table and exposed through a new REST endpoint. The Streamlit frontend gains per-post buttons to trigger, regenerate, and view infographics.

All pipeline stages must run without an NVIDIA GPU. Diffusion models (FLUX, Stable Diffusion, or any locally-run image-generation model) are explicitly out of scope. Image generation is handled through a pluggable `ImageProvider` interface whose default implementation requires no API key (`MockImageProvider`).

---

## Glossary

- **Pipeline**: The ordered sequence of steps — VisualSpec generation → background image generation → HTML rendering → PNG export → database persistence — executed for a single `PostModel`.
- **VisualSpec**: A Pydantic model representing structured visual metadata generated by Qwen3. Stored as JSON in the database.
- **ImageProvider**: An abstract base class with a single async method `generate(prompt: str) -> bytes` that returns PNG bytes. Implementations include `MockImageProvider` and `HuggingFaceImageProvider`.
- **MockImageProvider**: An `ImageProvider` implementation that returns a deterministic solid-color PNG without making any network calls. Used when `IMAGE_PROVIDER=mock` or when no API key is configured.
- **HuggingFaceImageProvider**: An `ImageProvider` implementation that calls the Hugging Face Inference API to generate a background image using a configurable model.
- **ImageModel**: The SQLAlchemy ORM model for the `images` database table.
- **ImageResponse**: The Pydantic response schema returned by the image generation API endpoint.
- **Infographic**: The final 1080×1080 (or aspect-ratio-appropriate) PNG file that combines the background image, DAY header, topic title, visual area, key points, takeaway, and footer/branding elements.
- **HTML Template**: The Jinja2 or f-string HTML/CSS document that is populated with `VisualSpec` fields and the background image, then passed to Playwright for rendering.
- **Playwright**: The headless browser used to render an HTML document to a PNG file. Runs locally with no GPU dependency.
- **Qwen3**: The locally-hosted LLM accessed via the Ollama API, used to generate `VisualSpec` JSON from post content.
- **PostModel**: The existing SQLAlchemy ORM model for the `posts` table (Phase 3). Must gain an `images` relationship in Phase 4.
- **DayTopicModel**: The existing SQLAlchemy ORM model for the `day_topics` table (Phase 2).
- **ImageStatus**: An enumeration of `ImageModel` lifecycle states: `PENDING`, `GENERATING`, `COMPLETED`, `FAILED`.
- **Settings**: The existing Pydantic-settings `Settings` class in `app/core/config.py`, extended with new image-related environment variables.
- **image_service**: The module `app/services/image_service.py` that orchestrates the full pipeline for a single post.
- **image_providers**: The module `app/services/image_providers.py` containing `ImageProvider`, `MockImageProvider`, and `HuggingFaceImageProvider`.
- **image_repository**: The module `app/services/image_repository.py` containing database CRUD operations for `ImageModel`.
- **images Router**: The FastAPI router in `app/api/routes/images.py` exposing `POST /api/images/generate/{post_id}`.

## Requirements

### Requirement 1: VisualSpec Data Model

**User Story:** As a developer, I want a well-defined, validated data model for the visual specification, so that all pipeline stages operate on consistent, schema-verified data.

#### Acceptance Criteria

1. THE `VisualSpec` SHALL be a Pydantic model with the following fields: `day_number` (int, ≥ 1), `title` (str, non-empty), `subtitle` (str), `visual_concept` (str, non-empty), `diagram_type` (str, one of: `"flowchart"`, `"hierarchy"`, `"comparison"`, `"timeline"`, `"list"`), `diagram_nodes` (list of str, 1–10 items), `key_points` (list of str, 3–5 items), `style` (str, one of: `"dark-tech"`, `"light-minimal"`, `"blue-gradient"`), `aspect_ratio` (str, one of: `"1:1"`, `"4:5"`, `"16:9"`).
2. WHEN a `VisualSpec` is constructed with all valid fields, THE `VisualSpec` SHALL serialize to a JSON-compatible dict containing exactly the above fields with their provided values.
3. IF `key_points` contains fewer than 3 or more than 5 items, THEN THE `VisualSpec` SHALL raise a `ValidationError`.
4. IF `day_number` is less than 1, THEN THE `VisualSpec` SHALL raise a `ValidationError`.
5. IF `diagram_nodes` is an empty list, THEN THE `VisualSpec` SHALL raise a `ValidationError`.
6. IF `title` is an empty string, THEN THE `VisualSpec` SHALL raise a `ValidationError`.
7. IF `visual_concept` is an empty string, THEN THE `VisualSpec` SHALL raise a `ValidationError`.
8. FOR ALL valid `VisualSpec` objects `v`, serializing `v` to JSON and then deserializing back SHALL produce a `VisualSpec` equal to `v` (round-trip property).

### Requirement 2: ImageProvider Interface and Implementations

**User Story:** As a developer, I want a pluggable image provider interface, so that background image generation can be swapped between a local mock and a cloud API without changing pipeline code.

#### Acceptance Criteria

1. THE `ImageProvider` SHALL be an abstract base class with an abstract async method `generate(prompt: str) -> bytes`.
2. THE `MockImageProvider` SHALL implement `ImageProvider` and return valid PNG bytes for any non-empty prompt string without making any network call.
3. THE `MockImageProvider` SHALL return deterministic output: calling `generate` with the same prompt string twice SHALL return byte sequences that decode to identical pixel data.
4. THE `MockImageProvider` SHALL return a solid-color PNG of at least 1×1 pixel, decodable by any standard PNG decoder.
5. WHEN `IMAGE_PROVIDER` is set to `"mock"` or is absent, THE `image_service` SHALL instantiate `MockImageProvider`.
6. WHEN `IMAGE_PROVIDER` is set to `"huggingface"`, THE `image_service` SHALL instantiate `HuggingFaceImageProvider`.
7. THE `HuggingFaceImageProvider` SHALL call the Hugging Face Inference API using the model ID specified in `HF_IMAGE_MODEL` and the bearer token from `HF_TOKEN`.
8. WHEN `IMAGE_PROVIDER` is set to `"huggingface"` and `HF_TOKEN` is an empty string, THE `HuggingFaceImageProvider` SHALL raise an `ImageProviderError` before making any API call, with a message indicating that `HF_TOKEN` must be configured.
9. WHEN `HuggingFaceImageProvider` is active and the Hugging Face Inference API returns a non-2xx HTTP response, THE `HuggingFaceImageProvider` SHALL raise an `ImageProviderError` with a message containing the HTTP status code.
10. WHEN `HuggingFaceImageProvider` is active and the Hugging Face Inference API call times out after 60 seconds, THE `HuggingFaceImageProvider` SHALL raise an `ImageProviderError` with a timeout message.
11. THE system SHALL operate fully without setting `HF_TOKEN` when `IMAGE_PROVIDER=mock`.

### Requirement 3: Image Database Model and Migration

**User Story:** As a developer, I want a database table for image metadata, so that the status, file path, and generation parameters of every infographic are persisted and queryable.

#### Acceptance Criteria

1. THE `ImageModel` SHALL map to a database table named `images` with the following columns: `id` (UUID PK, `Uuid(as_uuid=True)`), `post_id` (UUID FK → `posts.id` CASCADE DELETE), `provider` (String(100), non-null), `prompt` (Text, non-null), `visual_spec` (JSON, non-null), `file_path` (String(500), nullable), `width` (Integer, nullable), `height` (Integer, nullable), `status` (String(50), non-null, default `"PENDING"`), `created_at` (DateTime with timezone, non-null).
2. THE `ImageModel` SHALL use `Mapped`, `mapped_column`, and `Uuid(as_uuid=True)` (dialect-agnostic), never `postgresql.UUID`.
3. THE `PostModel` SHALL gain an `images` relationship to `ImageModel` with `back_populates="post"` and `cascade="all, delete-orphan"`.
4. THE Alembic migration file `0003_add_images_table.py` SHALL have `down_revision = "0002"` and create the `images` table with all columns and the FK index `ix_images_post_id`.
5. THE `downgrade()` function in migration `0003_add_images_table.py` SHALL drop the `ix_images_post_id` index and the `images` table.
6. WHEN a `PostModel` record is deleted, THE database SHALL cascade-delete all associated `ImageModel` records.
7. FOR ALL `ImageModel` records persisted and then retrieved by `id`, all fields SHALL equal the originally persisted values (round-trip property).

### Requirement 4: VisualSpec Generation via Qwen3

**User Story:** As a content creator, I want the system to automatically generate a structured visual specification from a LinkedIn post, so that I don't have to manually design the infographic layout.

#### Acceptance Criteria

1. WHEN the pipeline is invoked for a `PostModel`, THE `image_service` SHALL send a prompt to the Qwen3 model via the Ollama API requesting a `VisualSpec` JSON object.
2. THE prompt sent to Qwen3 SHALL include the post's `content`, the associated `DayTopicModel.title`, `DayTopicModel.day_number`, `DayTopicModel.main_subject`, `DayTopicModel.category`, and `DayTopicModel.difficulty`.
3. THE prompt sent to Qwen3 SHALL instruct the model to respond with only valid JSON matching the `VisualSpec` schema, with no additional prose, markdown fences, or `<think>` blocks.
4. WHEN Qwen3 returns a response containing a `<think>` block, THE `image_service` SHALL strip the `<think>…</think>` preamble before parsing JSON.
5. WHEN Qwen3 returns a response that cannot be parsed as valid `VisualSpec` JSON after stripping, THE `image_service` SHALL raise a `VisualSpecGenerationError`.
6. WHEN the Ollama API is unreachable, THE `image_service` SHALL raise a `VisualSpecGenerationError` with a message indicating the connectivity failure; other errors from Qwen3 (e.g., malformed but reachable responses) SHALL propagate normally without being wrapped.
7. THE prompt sent to Qwen3 SHALL be constructed from whatever `PostModel` and `DayTopicModel` fields are available; if some fields are null or absent, THE `image_service` SHALL still send the prompt with the available fields.

### Requirement 5: HTML/CSS Template Rendering

**User Story:** As a content creator, I want a visually consistent HTML-based infographic template, so that all generated images share professional branding and layout.

#### Acceptance Criteria

1. THE HTML template SHALL produce a document containing a DAY header showing the `day_number` formatted as `"DAY XX"` (zero-padded to 2 digits).
2. THE HTML template SHALL embed the `title` from `VisualSpec` as the main heading of the infographic.
3. THE HTML template SHALL embed the background image as a Base64-encoded data URI in an `<img>` element within the visual area section.
4. THE HTML template SHALL list each item from `key_points` as a separate bullet element.
5. THE HTML template SHALL include a footer or branding section containing a fixed brand string (e.g., `"#LearnWithAI"` or a configurable string).
6. WHEN `style` is `"dark-tech"`, THE HTML template SHALL apply a dark background color (e.g., `#0a0a1a` or equivalent) and light text.
7. WHEN `style` is `"light-minimal"`, THE HTML template SHALL apply a white or near-white background and dark text.
8. WHEN `style` is `"blue-gradient"`, THE HTML template SHALL apply a blue gradient background.
9. FOR ALL valid `VisualSpec` objects, the HTML template function SHALL return a non-empty string containing `<!DOCTYPE html>` or `<html`, a DAY header, the title, and all key points.
10. THE HTML template SHALL set the root element dimensions such that Playwright renders a PNG matching the target resolution for the given `aspect_ratio`: `1:1` → 1080×1080, `4:5` → 1080×1350, `16:9` → 1920×1080.

---

### Requirement 6: PNG Rendering via Playwright

**User Story:** As a content creator, I want the HTML infographic rendered to a high-quality PNG, so that the image is ready to upload to LinkedIn without any post-processing.

#### Acceptance Criteria

1. WHEN the HTML template is rendered, THE `image_service` SHALL use Playwright (headless Chromium) to take a full-page screenshot and save it as a PNG file.
2. THE rendered PNG SHALL have the pixel dimensions matching the `aspect_ratio` specified in `VisualSpec`: `1:1` → 1080×1080, `4:5` → 1080×1350, `16:9` → 1920×1080.
3. THE PNG SHALL be saved to the directory specified by `IMAGE_OUTPUT_DIR` (default `"images"`) with a filename of the form `{post_id}_{timestamp}.png`.
4. THE `image_service` SHALL create the `IMAGE_OUTPUT_DIR` directory if it does not already exist before saving the PNG.
5. WHEN Playwright fails to render the HTML (e.g., due to a missing browser binary or timeout), THE `image_service` SHALL raise a `RenderingError` with a descriptive message, regardless of whether any partial output was produced.
6. THE rendered PNG file SHALL be a valid PNG decodable by standard image libraries (e.g., Pillow) with dimensions readable from the file header.

### Requirement 7: Image Persistence and Status Lifecycle

**User Story:** As a developer, I want every pipeline execution to record its status and metadata in the database, so that successes and failures are auditable and the frontend can reflect the current state.

#### Acceptance Criteria

1. WHEN the pipeline begins for a `PostModel`, THE `image_repository` SHALL create an `ImageModel` record with `status="PENDING"` and return its `id`.
2. WHEN the `ImageProvider.generate` call begins, THE `image_repository` SHALL update the `ImageModel` status to `"GENERATING"`.
3. WHEN the PNG file has been saved successfully, THE `image_repository` SHALL update the `ImageModel` with `status="COMPLETED"`, `file_path` (the saved path), `width`, `height`, and the serialized `visual_spec`.
4. IF any pipeline step raises an exception, THEN THE `image_repository` SHALL update the `ImageModel` status to `"FAILED"` and the `image_service` SHALL not re-raise; instead it SHALL return a failure result.
5. THE `image_service` SHALL set the `provider` field to the class name of the `ImageProvider` instance used (e.g., `"MockImageProvider"`, `"HuggingFaceImageProvider"`).
6. THE `image_service` SHALL set the `prompt` field to the `visual_concept` string from `VisualSpec` that was sent to the `ImageProvider`.

### Requirement 8: Image Generation API Endpoint

**User Story:** As a frontend developer, I want a REST endpoint to trigger infographic generation for a post, so that the Streamlit UI can initiate and poll generation without directly coupling to the pipeline.

#### Acceptance Criteria

1. THE `images Router` SHALL expose `POST /api/images/generate/{post_id}` accepting a UUID `post_id` path parameter, and THE `images Router` SHALL be registered and configured in `app/main.py` under the prefix `/api/images` such that the endpoint is reachable in the running application.
2. WHEN the `post_id` does not exist in the database, THE `images Router` SHALL return HTTP 404 with a JSON body containing `"detail"`.
3. WHEN the pipeline completes successfully, THE `images Router` SHALL return HTTP 200 with an `ImageResponse` body containing `success=True`, the `ImageModel` fields, and `post_id`.
4. WHEN the pipeline fails at any step, THE `images Router` SHALL return HTTP 200 with an `ImageResponse` body containing `success=False` and `status="FAILED"`.
5. THE `images Router` SHALL be registered in `app/main.py` under the prefix `/api/images`.
6. THE `ImageResponse` schema SHALL include fields: `success` (bool), `id` (UUID), `post_id` (UUID), `provider` (str), `prompt` (str), `visual_spec` (dict), `file_path` (str or null), `width` (int or null), `height` (int or null), `status` (str), `created_at` (datetime).
7. WHEN `POST /api/images/generate/{post_id}` is called and the post already has an associated `ImageModel`, THE `images Router` SHALL overwrite the existing image record (or create a new one) and return the updated `ImageResponse`.

### Requirement 9: Settings Extension

**User Story:** As a developer, I want all image-related configuration loaded from environment variables via the existing `Settings` class, so that deployment configuration remains centralized and consistent with Phases 1–3.

#### Acceptance Criteria

1. THE `Settings` class in `app/core/config.py` SHALL include the following new fields: `image_provider` (str, default `"mock"`), `hf_token` (str, default `""`), `hf_image_model` (str, default `"stabilityai/stable-diffusion-xl-base-1.0"`), `image_output_dir` (str, default `"images"`).
2. WHEN `IMAGE_PROVIDER` is absent from the environment, THE `Settings` SHALL use the default value `"mock"`.
3. WHEN `HF_TOKEN` is absent from the environment, THE `Settings` SHALL use an empty string as the default, and the system SHALL still operate correctly when `IMAGE_PROVIDER=mock`.
4. THE `.env.example` file SHALL be updated to document the four new environment variables with their default values and brief comments.

### Requirement 10: Streamlit UI — Infographic Actions

**User Story:** As a content creator, I want per-post buttons in the Content Calendar tab to generate, regenerate, and view infographics without leaving the Streamlit interface.

#### Acceptance Criteria

1. WHEN the Content Calendar tab renders a post row, THE Streamlit UI SHALL display three additional buttons: `"Generate Visual"`, `"Regenerate Visual"`, and `"View Infographic"`.
2. WHEN the user clicks `"Generate Visual"`, THE Streamlit UI SHALL call `POST /api/images/generate/{post_id}` and display a success or error message based on the response `success` field.
3. WHEN the user clicks `"Regenerate Visual"`, THE Streamlit UI SHALL call `POST /api/images/generate/{post_id}` and display a success or error message, overwriting any previously displayed infographic.
4. WHEN the user clicks `"View Infographic"` and the image `status` is `"COMPLETED"`, THE Streamlit UI SHALL display the LinkedIn post text, a JSON expander showing the `visual_spec`, and the infographic PNG using `st.image()`.
5. WHEN the user clicks `"View Infographic"` and no completed image exists for the post, or when the `status` is `"COMPLETED"` but the referenced file is missing from disk, THE Streamlit UI SHALL display an informational message prompting the user to generate a visual first.
6. THE Streamlit UI additions SHALL be placed inside the existing Content Calendar tab without altering any other tab's layout or behavior.

### Requirement 11: Test Coverage

**User Story:** As a developer, I want a comprehensive test suite for the image pipeline, so that regressions are caught automatically and all acceptance criteria are verifiable.

#### Acceptance Criteria

1. THE test file `backend/tests/test_images.py` SHALL contain tests using SQLite in-memory + FastAPI `TestClient` + `AsyncMock` for external calls, consistent with the existing Phase 1–3 test patterns.
2. THE test suite SHALL include a `VisualSpec` Pydantic validation test covering at least one valid input and at least three invalid inputs (too few `key_points`, `day_number < 1`, empty `title`).
3. THE test suite SHALL include a property-based test (Hypothesis) verifying that `VisualSpec` serialization is a round-trip: for all valid `VisualSpec` inputs, `VisualSpec.model_validate(v.model_dump()) == v`.
4. THE test suite SHALL include a test verifying that `MockImageProvider.generate` returns bytes that are a valid PNG (PNG magic bytes `b"\x89PNG\r\n\x1a\n"` at offset 0).
5. THE test suite SHALL include a test verifying that the HTML template function returns a string containing the expected DAY header, title, and all key points for a given `VisualSpec`.
6. THE test suite SHALL include a property-based test (Hypothesis) verifying that the HTML template always contains the title field for arbitrary valid `VisualSpec` instances.
7. THE test suite SHALL include a test verifying that Playwright renders a PNG file of the correct pixel dimensions (1080×1080 for `aspect_ratio="1:1"`).
8. THE test suite SHALL include a test verifying that an `ImageModel` persisted to the in-memory SQLite database can be retrieved by `id` with all fields intact (persistence round-trip).
9. THE test suite SHALL include a test verifying that when `ImageProvider.generate` raises an exception, the saved `ImageModel` has `status="FAILED"`.
10. THE test suite SHALL include a test for `POST /api/images/generate/{post_id}` happy path using `MockImageProvider`, asserting HTTP 200, `success=True`, `status="COMPLETED"`, and non-null `file_path`.
11. THE test suite SHALL include a test for `POST /api/images/generate/{non_existent_id}` asserting HTTP 404.
12. THE test suite SHALL not break any of the 54 existing tests in Phases 1–3 (zero regressions).

---

### Requirement 12: Non-Regression and Architecture Constraints

**User Story:** As a developer, I want Phase 4 additions to be strictly additive, so that the existing Phase 1–3 functionality, models, routes, and tests are not broken.

#### Acceptance Criteria

1. THE Phase 4 implementation SHALL NOT modify any existing model class (`ContentPlanModel`, `DayTopicModel`, `PostModel`) except to add the `images` back-reference relationship to `PostModel`.
2. THE Phase 4 implementation SHALL NOT modify any existing schema file, service file, or API route file from Phases 1–3.
3. THE Phase 4 implementation SHALL NOT use `postgresql.UUID` anywhere; all UUID columns SHALL use `Uuid(as_uuid=True)` (dialect-agnostic).
4. THE Phase 4 implementation SHALL NOT require FLUX, Stable Diffusion, or any locally-run neural image diffusion model.
5. WHILE running the full test suite (`pytest backend/`), THE system SHALL report zero failures across both Phase 1–3 and Phase 4 tests.
6. THE new Alembic migration `0003_add_images_table.py` SHALL NOT alter any table other than creating `images` and adding `ix_images_post_id`.
